# 需求分析与成熟方案选型

版本：1.0；调研日期：2026-11-13。适用范围：单公司、500 人以内、Windows Piora、管理员与授权只读账号、自建后端。

## 要回答的实际问题

1. 有多少**人**使用 Piora，哪些人每天在用，哪些安装还未绑定到人？
2. 每个人每天提交多少人工 Query、打开几次、实际活跃多久，任务运行多久？
3. 各员工、部门、模型、版本消耗多少 Token，失败/重试/辅助调用各占多少？
4. AI 文件工具实际新建/修改多少文件、增加/删除多少行？哪些操作无法可靠计量？
5. 数据最后何时收到，设备是否积压，是否存在未知用量、丢弃、拒收或未覆盖能力？

“完美看到统计”需要可解释的口径和覆盖状态。低频上传意味着看到的是最近已收到的数据，不能据此显示实时在线人数；代码行数是文件工具落盘变化，不代表代码质量、员工效率或最终被 Git 接受的贡献。

## 为什么不直接枚举 C:\Users

C:\Users 下的目录包含其他本地账号、旧账号和系统配置文件，目录数量不是 Piora 使用人数。采集进程通过 os.userInfo().username 获取**当前账号**，同时生成安装 UUID。用户名可能重复、更名或多人共享，因此不做身份认证或唯一员工标识。管理员确认 Windows 账号/设备与员工的对应关系，才计入已确认人数。多设备绑定同一员工后人数去重；未绑定安装单独展示。[Node.js os.userInfo](https://nodejs.org/api/os.html#osuserinfooptions)

## 成熟产品比较

| 方案 | 已有能力 | 需要补的部分 | 本项目判断 |
|---|---|---|---|
| Countly | Windows SDK、会话、自定义事件、用户资料与离线队列 | Piora Query、实际模型调用及可靠代码计量；员工归属管理及特定报表；需核对所选版本商业能力 | 最接近完整产品分析平台的候选。若愿意采用其后台并采购相应能力，可缩短通用统计开发 |
| PostHog | 事件、用户分析、产品看板 | Windows 活跃时长、文件落盘统计仍需自定义；自行运维自托管版本 | 官方说明自托管不提供支持保证，不作为本项目首期核心依赖 |
| Langfuse | LLM 调用、Token、成本、链路观测 | 桌面打开次数、Windows 人员映射、活跃区间、代码文件变化 | 可作为后续模型调试系统；不能独立替代本需求 |
| Aptabase | 简单应用事件统计 | 不以持久用户追踪为目标，难支撑实名员工每日历史 | 不匹配当前逐员工长期统计 |
| PostgreSQL + Metabase | SQL 报表、自建 BI | 客户端可靠记账、鉴权、去重、身份管理仍需开发；行列权限有版本限制 | 可做临时分析工具，定制业务看板仍独立建设 |
| 专用轻量后端 + 自有 UI | 完整控制统计语义、人员归属和同步策略 | 需要实现采集与聚合，但规模可控 | **选用**；复用成熟存储、协议、图表与鉴权组件 |

上述能力来自官方资料：[Countly Windows](https://support.countly.com/hc/en-us/articles/360037754691-Windows)、[Countly SDK 机制](https://support.countly.com/hc/en-us/articles/21551709869980-How-SDKs-Work)、[PostHog 自托管](https://posthog.com/docs/self-host)、[Langfuse 自托管](https://langfuse.com/self-hosting)、[Aptabase 文档](https://aptabase.com/docs)、[Metabase 行列权限](https://www.metabase.com/docs/latest/permissions/row-and-column-security)。

选型判断是结合本项目的推论：没有一个产品无需 Piora 埋点，就能同时得到当前要求的真实活跃时长、人工 Query、包含重试的全部 Token 和文件工具落盘变化。自建的核心价值是统一这些口径。首期不重复实现通用 BI 或完整 LLM trace 产品。

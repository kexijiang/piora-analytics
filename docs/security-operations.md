# 安全、部署与运维

## 数据范围

采集允许列表只有用户名/设备显示名、安装 UUID、发生时间、版本、来源分类、匿名业务 ID、时长、计数、模型标识和文件 HMAC 分类。不上传提示词、回复、代码、diff、路径、仓库名、环境变量、模型密钥和错误堆栈。用户名是员工匹配线索，保存在内部服务。

企业分发前在 Piora“组织统计”页面明确展示采集范围和管理员联系方式。这里是具体产品设计，不推断任何法域合规结论。用户名不能单独证明真实人身份，不做不可验证的员工效率评分。

## 认证实现要求

- 后台使用 Argon2id 密码哈希；参数参考选定实现的最新官方文档并通过服务器耗时测试，目标验证约 100–300ms。密码不少于 12 字符，禁止固定默认管理员密码。
- 首位 admin 通过一次性 CLI 创建，密码仅从临时安全环境传入；命令不得把密码写入 shell history。生产角色拆分参见 deployment.md。
- 登录连续失败按账号+IP 组合节流：5 次/15 分钟后阻止该窗口的继续尝试；安全消息统一，不暴露账号存在与否。管理员可撤销会话；12 小时绝对、2 小时空闲过期。
- 安装秘密 32 随机字节，以 pa1.credential_id.secret 发送；服务端 HMAC(secret,server_pepper) 恒时比较，pepper 放 secret store，数据库备份中无明文。
- Enrollment key 最多 30 天且有限使用次数，只允许注册。每次轮换/绑定/导出/策略变更/账号变更记审计。

所有导出下载重新校验会话与任务归属；私有文件不暴露匿名 URL。日志脱敏 Authorization/Cookie/Set-Cookie/X-CSRF-Token/password/secret；拒收事件只记录类型/原因/id，不把不受信任 payload 写日志。

## 生产部署清单

1. 配置内部域名、TLS、反向代理（上报未压缩上限 256 KiB；压缩请求独立压缩/解压上限，防解压炸弹）。
2. 创建 PostgreSQL 18、迁移角色与运行角色，迁移后退出 DDL 身份；安装 btree_gist。
3. 配置服务器 pepper、session/encryption keys、私有导出存储路径与数据库凭证；不得写入 Git。
4. 启动 API/Worker/静态 UI；health/live 只表示进程，ready 校验数据库与迁移版本，不回显配置细节。
5. 创建首位 admin、部门/员工、有限 enrollment key；由企业分发配置给 5 台试点 Windows。
6. 验证一次离线补传、重复批次、员工纠错、导出、未知 Token、睡眠/锁屏后，再扩到 50、最后全员。

已提供 Dockerfile、compose.yaml、Caddy 配置示例和初始化 CLI；详见 [部署步骤](deployment.md)。容器/TLS/备份恢复仍需在实际服务器验收。

## 可观测性

API 自身仅统计请求耗时、状态、批次数、入库/去重/拒收条数；不能把客户端原始内容再发第三方日志服务。Worker 指标：积压数、最老任务年龄、重试数、处理时延、租约过期数、分区创建状态、清理延迟。客户端上报 queue_events/bytes/drop/quarantine/clock codes。

告警建议：聚合 lag>5min 持续 10min、入库 5xx>1% 持续 5min、磁盘剩余<20%、未来分区不足两个月、备份>24h 未成功、重复内容冲突>0。安装超过 40min 无数据在看板标“报告较旧”；超过 24h 可按团队约定通知管理员，不能自动推断员工未工作。

## 灾难恢复与升级

每日全量/增量加密备份 + WAL；每月临时环境恢复演练，核对 receipt 与原始分区及汇总一致。迁移先兼容读写，服务端先部署、客户端后部署；客户端采集 kill switch 保留。迁移回滚优先回滚应用，结构破坏需备份恢复方案，不能靠自动 drop 重建。

统计数据可修改的管理入口包括身份纠错、保留配置；任何删除/缩短保留先显示影响范围，提交后审计。原型的演示重置仅清本地虚构状态，不代表生产有无审计一键清库功能。

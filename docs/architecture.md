# 后端架构与规模设计

## 组件

~~~mermaid
flowchart LR
  E[Windows Electron 主进程] --> Q[(本地 SQLite WAL)]
  N[Piora Node 模型/工具/命令管线] --> Q
  Q --> U[单一上传器: 随机 25–35 分钟]
  U -->|TLS: 事件批次| A[Node.js API]
  A -->|一个事务| P[(PostgreSQL 18)]
  P --> W[独立 Worker]
  W -->|日汇总/导出| P
  D[React 管理看板] -->|同源会话| A
  A --> P
~~~

- apps/api：已实现 Fastify + Node.js ESM，使用 JSON Schema/Ajv 验证，依赖锁定在 package-lock。认证、限流、批量接收、报表、管理接口；不开模型代理，不接受提示词。
- apps/worker：同仓库独立进程，消费 PostgreSQL 持久任务，聚合、导出、保留清理、提前建分区。首期使用 SKIP LOCKED 租约，不需 Redis/Kafka。
- apps/dashboard：React + Vite + ECharts；生产静态产物由反向代理托管，/v1 转发 API。
- packages/contracts：OpenAPI 生成的 TypeScript 类型；客户端/后端消费同一协议，事件运行时验证使用 JSON Schema。

浏览器只访问同源后端，终端安装凭证只存在本机主进程。每个安装调用一次注册接口，之后仅向批量上报接口发统计；临近过期另调用轮换接口。员工不注册后台账号。

## 首期容量假设

这是规划估算，不是压测结果。500 个安装每天运行 8 小时、每分钟一个活动事件约 24 万事件/日；每人 80 Query、每 Query 平均 4 次模型请求、3 次文件操作，再加状态/任务事件，约 100 万至 150 万事件/日。若实际使用更重，容量近似线性增长。

平均每个安装工作日约 16 轮上传，500 台约 8,000 轮/日；单轮按 500 条/256 KiB 分批。不是 8,000 条事件，也不是每轮只会有一次 HTTP。目标压测按 500 台同时开机、离线 7 天恢复、每秒 100 个批次突发，验证限流和退避。

初始建议 4 vCPU、8 GiB 内存、至少 200 GiB 可扩容 SSD（仅起点）。原始事件、JSONB、索引、90 天明细可能占数百 GiB；按实际平均事件字节和索引放大系数监测扩容，不能保证 200 GiB 覆盖全部保留期。备份空间独立计算。具体上线规格以压测与一周试点数据决定。

## 服务目标与故障边界

| 项目 | 目标 / 行为 |
|---|---|
| 正常数据新鲜度 | 在线持续运行客户端：最近产生的数据通常 40 分钟内可见；由最长 35 分钟间隔 + 处理时间构成目标，不是每条事件 SLA |
| 入库后聚合 | p95 < 60 秒，p99 < 5 分钟（待压测） |
| 上传确认 | 只有数据库持久提交后 ACK；数据库不可用 503 |
| 聚合失败 | 原始数据仍在；租约到期恢复，日重算幂等 |
| 看板延迟 | 总览/日表 p95 < 2 秒，明细 < 3 秒（待验证） |
| 客户端体验 | 采集不阻塞模型/工具；持久队列失败显示健康缺口，软件仍可用 |

报表在数据库事务中读取已提交聚合，不冻结跨请求快照，meta.aggregation_as_of 与 data_through 告诉用户“聚合时间”和“已处理事件时间”。它们不能承诺所有设备在此前都已上传。页面刷新只刷新后台数据，不主动要求全部客户端上报。

## 扩展路径

先优化时间/组织索引、按日物化与分页；出现持续聚合 lag 或 500 台实测容量不足再分离数据库/Worker、增加分区和读副本。只有达到 PostgreSQL 分析瓶颈后才评估 ClickHouse。保留协议和事实模型以便迁移，不在首期叠加不必要组件。

服务端部署机器不限 Windows；“只考虑 Windows”适用于 Piora 客户端。生产建议 Linux 容器 + PostgreSQL 持久卷；客户端采集只实现 Windows x64。
